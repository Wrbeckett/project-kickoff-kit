# Project Kickoff Kit

Use this when the person says "start a new project", "set up a project", "kick off <project>", "audit this project", "review my project's workflow", "hand this project to <name>", "join this project", "take over this project", "close this project", "what's next?", or connects a folder containing KICKOFF.md or AUDIT.md.

**Finding the kit:** the full process lives in the Project Kickoff Kit: installed as a plugin, this skill's own folder holds the whole kit (in its kit/ subfolder); otherwise a connected "Project Kickoff Kit" folder; otherwise the kit's GitHub page (https://github.com/Wrbeckett/project-kickoff-kit). It has 00 QUICK START, 00 START HERE, 01 New project/KICKOFF.md + Interview question bank.md, 02 Existing project/AUDIT.md, 03 Templates/, 04 Prompts to copy, 06 Models and sessions cheat sheet, 07 Join or take over a project/ (HANDOVER-PACK.md, JOIN.md, TAKEOVER.md), 08 Close a project/CLOSE.md, 10 What's next/NEXT.md, 03 Templates/Presets/, 09 Shared folder/Working from a shared folder.md. Read the file for the job and follow it: it wins over this summary. If none is reachable, say so plainly and help the person install the plugin or connect the kit folder; you may answer questions from this summary, but don't build a project setup from the summary alone.

## What's next? (Prompt 18)
Follow 10 What's next/NEXT.md: read only what's needed (change log, handover §3/§10/§12, the person's brief, trackers), skip anything that still waits on something, and answer in 5 lines max: the one next step, where (chat, model, effort), minutes, up to two follow-ups, and any important blocker. Offer to start; don't start without a yes.

## Kickoff extras
Offer a starter preset (03 Templates/Presets/) when the project fits one; its answers are suggestions to confirm. Show the blueprint in sections with an OK on each. Include a "what could go wrong" list (3–5 reasons, warning signs, what the setup does) in the handover's §11. After building, ask the owner for the fresh chat test (Prompt 19).

## Close or pause a project ("close this project", Prompt 15)
Follow 08 Close a project/CLOSE.md: ask close or pause; list scheduled tasks and open items (read only); after the OK turn tasks off (never delete), write "<Project> - Final summary.pdf", archive drafts, mark the handover CLOSED or PAUSED, list what's still shared, and note lessons (MY-DEFAULTS, kit feedback).

## Always
- Write for the person in plain words: short sentences, exact menu and file names, minutes per step.
- **Everything is a default.** Start from the owner's MY-DEFAULTS.md (their own copy, in a connected folder) if there is one; do it the owner's way when they want something different; record every difference in the project's PROJECT-CHOICES.md, which wins over the kit and is never undone by reviews or upgrades without asking. "change: …" to Lead updates every affected file at once.
- **Never assume.** Ask about anything unclear, missing or contradictory, 3–5 questions at a time, multiple choice where possible (your recommendation first).
- Nothing is created, connected, bought, posted, sent, moved or deleted without the person's OK. Audits only read.
- Check every file you write; never overwrite in place (new never-used name, check, then replace); never delete (use _to_delete).
- **Fit the owner's Claude usage.** Always ask which Claude plan they have, when weekly usage resets, and what share this project may use. Size sessions, reports and scheduled runs to fit (USAGE-PLAN.md), so they never run out mid-week.
- **Match the model to the job.** Recommend a model and effort for every session, scheduled task and kind of work (MODEL-GUIDE.md; kit defaults in "06 Models and sessions cheat sheet"): Opus 5.5 at Medium for interviews, audits (High), Lead, planning, research and judgment work; Sonnet 5.5 for clear, well-scoped work and routine reports; Haiku 5.5 for reminders and quick checks; Fable 5.2 only for the hardest long jobs, with the owner's OK where it uses paid credits. Only models the owner's plan has. When a job misses: fix the prompt, raise effort, then move up a model.
- **Home computer:** each project has one Mac or PC that stays on (awake while plugged in, online, Claude app open, folders synced). Start sessions and create scheduled tasks there; a task that uses the project's files runs on the computer its chat is linked to, so check that first. Tasks that need no files run in the cloud. Tell the owner which computer and approval setting each task got. Laptop or often-off computer: agree a **work window**, schedule computer tasks inside it, add a cloud-only reminder before it (phone and/or email, as chosen) and a "done, you can close it" message at the end; computer tasks catch up on missed windows.
- Keep the setup as light as the project needs: recommend a **setup level** (Solo / Standard / Team, 03 Templates/Setup levels.md) and build only what it calls for.
- **Sensitive information: the owner decides.** Always ask (question bank §5b: what personal information, which privacy or AI policy, NDAs) and record their rule in their words as rule 15; in a takeover ask the new owner fresh. Until it's set, keep personal information about other people out (a temporary hold, not a rule you chose).
- **Team updates:** only the owner can post in the Lead chat; everyone else uses UPDATES-INBOX.md, which Lead reads at the start of every run.
- **Shared folder (Team level):** one shared project folder everyone connects; one owner per shared file (handover table; others send ASK: lines); read CHANGES.md before every job and add a line after changing a shared file; use what ASSETS.md marks CURRENT; report sync-conflict copies, never pick one (09 Shared folder). **Project lead** named in the handover, changed only with the current lead's OK (Prompt 17); **protected** files change only with the lead's OK. **Backups:** copy a shared file to Archive/_versions/ before editing; a weekly snapshot task zips 00 Admin, 03 Final, 04 Assets (keep 8; older to _to_delete); "restore <file> to <when>" (Prompt 16): list versions, show differences, save the current one, restore after the lead's OK, log it.
- **Kit version:** record it in the handover; for projects on an older version, offer what's new in the kit's CHANGELOG.md (Prompt 9). Problems with the kit itself go to KIT-FEEDBACK.md.

## New project
1. **Look around silently**, and **stop first if this chat isn't inside a Claude Project with the project folder connected**: walk the owner through making them, then restart in a new chat there (this chat becomes the Lead). Then check: the connected folder, available tools/connectors/skills, whether this chat is in a Claude Project (if not, explain how to make one).
2. **Interview in rounds:** project and success measures, deadlines; people and who decides; kinds of work, what repeats; where files/accounts/sites live and what Claude may touch; rules, budget, never-do list, privacy; time, rhythm, time zone; **Claude plan, weekly reset, usage share for this project, heavy days, what to do near the limit, models in their picker;** how they like updates; risks and unknowns. Read back a 10-line summary and confirm.
3. **Blueprint (PROJECT-BLUEPRINT.md), approved before building:** setup level; goal; folder structure; sessions (a Lead session + only the work sessions needed); trackers only where work passes between sessions; rhythm (brief, reports, weekly review); **usage plan** (each run's cost light/medium/heavy, expected week vs the share, "pause first" list; cut the rhythm if it doesn't fit); **model plan** (model + effort per session, scheduled run and kind of work: MODEL-GUIDE.md); tools (plugins, connectors, skills, apps; plugins always optional, marked installed or worth adding), each marked CLAUDE CAN DO / YOU DO / NEEDS A CONNECTOR; rules; open questions.
4. **Build after a clear yes:** folders; PROJECT-HANDOVER.md, SESSION-BRIEF-<name>.md per session, WORKFLOW-RULES.md, trackers, WORKFLOW-REVIEW.md, CHEAT-SHEET.md (with each session's model), USAGE-PLAN.md, MODEL-GUIDE.md; "<Project> - START HERE.pdf" and "<Project> - Session prompts.pdf" (look at every page); scheduled tasks only with OK, each complete enough to run in a fresh chat.
5. **Hand over:** this chat becomes "<Project> – Lead"; 5 lines max on what's set up, the PDF to open, the first session to start, the first thing to do.

## Existing project
1. **Inventory (read only):** folders and files, the Claude Project's docs, past chats (past-chats search), old handovers and briefs, scheduled tasks, websites and links, connected apps, sharing, **Claude usage (plan, reset, what each scheduled task and kind of work costs, repeated or unread work, which model each chat and task runs on)**. Say which sources you couldn't reach and ask to add them. Don't copy secrets.
2. **Questions:** current goals and deadlines, who decides, which docs are current, what works, what frustrates, rules, time and rhythm; 10-line summary.
3. **Report: "<Project> - Audit and recommendations.pdf":** bottom line; what exists; what's working; problems with evidence and cost; recommended workflow (setup level, folders, sessions, trackers, rhythm, rules); tools; **usage and efficiency, model fit (current → recommended)**; clean-up list; ONE numbered decision list, each marked CLAUDE CAN DO / YOU DO / NEEDS A CONNECTOR. The person answers "OK 1, 3; not 2".
4. **Build only what's approved**, then the START HERE and Session prompts PDFs and (with OK) scheduled tasks.
5. **Hand over** as above.

## Hand off, join or take over (07 Join or take over a project)
- **Giver** ("hand this project to <name>", Prompt 11): follow HANDOVER-PACK.md. Read only; ask JOIN or TAKEOVER, who receives it, and the giver's role afterwards (owner / adviser / fully handed off). Fill the HANDOVER-PACK template, labelling every fact [DECIDED], [CONFIRMED BY <receiver>], [GIVER'S NOTES], [CLAUDE'S SUGGESTION] or [VERIFY]. Leave out by default: the giver's own plan and usage, the giver's private notes and opinions about the receiver, logins and keys, other people's personal information. For a takeover, offer a zip (one project-named folder with the pack, handover files and a plain-words READ ME FIRST.txt; never logins or the kit). The giver reviews it and sends it; Claude never sends it.
- **Joiner** (Prompt 12, JOIN.md): confirm the pack in one summary; interview only about their role, access, plan, models and rhythm; build MEMBER-<name>.md, their own briefs and PDFs; write nothing in the owner's files except UPDATES-INBOX.md lines (ASK: for anything the owner should change).
- **New owner** (Prompt 13, TAKEOVER.md): go through the pack (decided/confirmed: "still right?"; notes and suggestions: keep / change / drop; verify: ask); only their answers are decisions; fill the gaps from the question bank; then KICKOFF.md from the blueprint step. Record "started by / taken over" in the handover and the giver's adviser role if any.

## Standard workflow rules to offer
Read-first before every job; handoff after every finished item; one update channel (the Lead session; everyone else writes to UPDATES-INBOX.md); the Lead coordinates but doesn't do others' work; numbered brief items and shorthand updates; every decision has a deadline and a safe default (never for money, posting, emails, deleting, deploying, terms or workflow changes); one daily "do it now" block; weekly trim of briefs and a handover of about 2 pages; a sensitive-information rule; the owner's choices win (PROJECT-CHOICES.md); planned fresh chats; a weekly review + audit with tools and connector suggestions; scheduled runs start from nothing, so give them full instructions and fallbacks; **usage budget: heavy jobs early in the usage week, runs stop early when nothing's new, read only what's needed, reuse scripts, fresh chats on time, weekly pace check; model fit: every session and scheduled run has its model and effort in MODEL-GUIDE.md, checked in the weekly review.**
